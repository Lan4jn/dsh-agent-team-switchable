# 模型路由使用说明（dsh-team-member-model）

这份说明只讲清三件事：插件在什么时刻决定「谁跑哪个模型」、两个界面入口各改什么、出问题按什么顺序查。
本文按 0.7.12 适配 DSH 0.2.2-rc.3 的目标编写；后端及完整回归尚在验证。团队关系以会话 ID 识别，Client 按 `subagentCatalog` 寻根，缺失或歧义时不开放入口，活动名单由 Host 核验。

---

## 一、先分清两组概念

**路由成员 ≠ Agent Team 队员。**
「成员」是插件自己的配置行：一个固定名字 + 若干「绑定」，用来决定子 agent 跑什么模型。「队员」是 DSH 官方的团队成员。两者可以同名，也可以毫无关系——成员表里叫 `budget` 的行，和官方队员 `budget` 没有绑定关系。

**两种「手动」不是一回事。**
设置页里的 `pick`（手动指定成员）仍属**自动路由体系**：只是跳过规则匹配，候选链和失败回退照旧。
团队菜单里的「固定分配」属**手动固定**：一旦生效就不再做运行期回退。

**基本术语**

| 词 | 含义 |
| --- | --- |
| 成员（member） | 一个固定名字，如 `expert`、`budget`；规则 `use`、`pick`、摘除、权重都按它 |
| 绑定（binding） | `provider + model + 可选思考档位`；一个成员可有多条，**顺序 = 渠道优先级** |
| 规则（rule） | 「什么情况用哪个成员」，条件之间是 AND，按顺序首条命中 |
| 策略（policy） | 成员表 + 规则 + 排序方式 + 回退 + 分类器，整份保存 |
| 团队固定分配 | 官方队员的「新队员默认」与「某队员下一轮的选择」，和策略分开保存 |

思考档位：**团队菜单里的下拉**只在该模型真公布了非空档位时才可选，否则置灰；设置页的绑定编辑器仍允许手填模型没公布的档位（适配器可能接受未公布的写法，但风险自负）。模型名里带 `high` 不代表它接受 `high`；不填档位就省略该字段，交给模型默认，别写空字符串。

---

## 二、两个入口，各管一段

**入口 A：设置 → 模型路由** —— 配成员、绑定、规则、排序方式、回退、分类器、`pick`。只管**自动路由**。

**入口 B：会话头部齿轮 → 团队模型设置** —— 只做官方队员的**固定分配**：给某队员指定下一轮模型，或设置「之后新增队员的默认」。它不改成员表，也不受成员表为空影响。

**Lead 自己永远不参与路由**，换 Lead 模型请用界面上的模型选择器。

覆盖范围：团队成员与后台子代理两个入口都生效；一次性子代理只受自动路由影响；`fork` 通道默认**不纳管**（改路由会丢父会话前缀的缓存复用，要用请在设置页打开 `allowFork`）；调用方自己指定了模型（自带 `agentOptions`）的路径，插件不覆盖。

---

## 三、优先级：五选一

团队队员每次请求都按这个顺序判定，前一条成立就用它：

1. **队员覆盖**：团队菜单给这个队员设的模型，且已经进入下一轮才生效；同一轮内维持改动前的旧值。
2. **创建时显式指定**：创建这个队员时调用方真的给了 provider 与 model。
3. **默认快照**：队员创建那一刻的「新队员默认」被快照下来，之后改默认不会回头改它。它**不等于 Lead 当前模型**。
4. **自动路由**：按成员表 + 规则规划。
5. **继承**：以上都没有，就用官方原本给它的模型。

前三级是**手动固定**：本插件不会为它自动换候选成员（官方底层自身是否重试由 DSH 决定，不在本插件管辖内）。第 4 级（含 `pick`）是自动体系，候选链上的延迟回退（Deferred Failover）照常生效：0.7.10 在 `agent/inbox/claimed` 准备前（带 per-turn guard）调用 `agent.model.select()` 确定模型；若运行期遇到 408/429/5xx 等错误，推进 rest 阶梯与沉底并记 `trace deferred`，当前 step 错误如实放行交官方处理，下一轮 turn 自动选用下一候选（明确不作同 step 跨模型伪重试）。

`members` 为空只关闭第 4 级，**不会**影响前三级的固定分配——这就是「成员表清空了，团队菜单设的模型还在生效」的原因。（例外：`match` 通配不为空时，插件会从模型目录扩充候选，此时自动路由仍然在工作。）

## 四、什么时候生效（最容易误判）

- **准备前正式选择**：0.7.10 严格对齐官方 AgentLoop 生命周期。模型选择迁移至 `agent/created`（serial 等待异步就绪）与 `agent/inbox/claimed`（同步消息认领后、step 模型 snapshot 之前，带 per-turn guard）通过官方 API `agent.model.select(selection)` 确立模型，避开 `session/event` 中 `turn/start` 可能的提交重入；请求阶段（`agent/request`）严格保持配置一致，彻底消除准备与请求冲突。
- 子 agent **创建时**决定一次：按当时策略算出「首选 + 有序候选链」，通过 `agent/created` 或首轮准备前注入。
- 运行期**不会**每轮重读策略。所以改规则、改成员表主要影响**之后新建**的子 agent；已经在跑的成员不会被立即换模型。
- 想让某个官方队员换模型，用**团队菜单**指定，它在**下一轮生效**（不是当前轮中途切换）。注意「恢复继承」清的是**之后新增队员的默认**（`target: null`），**不会**清掉已有队员的覆盖；当前界面也没有单行「清除覆盖」按钮，已有队员要改只能再选一个具体模型，或用接口 `PUT /teams` 传 `target: 队员 id` + `selection: null`——它回到的是创建时的来源/默认快照，**不保证**等于 Lead 当前模型。
- 失败回退是**下一轮生效（Deferred Failover）**：当当前 turn 的请求失败后，推进候选阶梯并在下一个 turn 开始时选择新候选，当前 turn 的失败直接报告给官方与用户。

一句话：**规则对新创建生效，团队菜单与失败回退均对下一轮生效**。

如果创建时调用方明确提供 `agentOptions`，创建期自动注入不会覆盖该选择；模型选择在步骤准备前完成，请求阶段不更改已锁定的模型。

## 五、自动路由怎么算

1. 有 `pause` 规则命中，先把 `use` 指到的成员从候选里摘掉。
2. `pick` 有值就跳过全部规则，直接选它指到的成员。
3. 规则从前往后匹配，**第一条全条件成立的赢**；命中不到成员就继续下一条。
4. 没命中时，`fork` 通道先看亲和（同父会话上次的成员，为复用缓存）；`spawn` 不看亲和，否则轮转永远轮不起来。
5. 仍没有就按 `order` / `rotate` / `weight` 取第一个成员。

选中成员后的候选链：**该成员的全部可用绑定（按数组顺序）→ 其它成员按排序方式排好的绑定**。所以回退是「先换渠道，再换成员」。

绑定的 `off`，或落在自身时段窗**之内**（这个渠道在此时段停用）→ 该渠道不参与，窗口之外照常可用；成员的 `off` 或出现在摘除名单 → 整个成员不参与；最近失败进入休息或被限流沉底的绑定不删除，只排到候选末尾。

**权重不影响「规则命中的首选」**，但没被选中的其它成员仍按排序方式排在候选链后面，所以它会影响回退顺序：权重是按游标推进的近似加权，不是精确概率、也不是按次数均分。

## 六、规则怎么写

条件全部可选，同一条里写多个就是 AND；`use` 必填（成员名）。

| 字段 | 含义 |
| --- | --- |
| `use` | 命中后用哪个成员 |
| `label` | 创建请求的描述做通配（`*review*`） |
| `member` | 官方队员名做通配 |
| `intent` | 分类器判定的意图（需开启分类器） |
| `channel` | `spawn` / `fork` |
| `continuable` | `true` 团队/后台，`false` 一次性（常用来写兜底） |
| `folders` / `exceptFolders` | 父会话工作目录 |
| `tokens` | 父会话 token 至少达到 |
| `effort` | 父会话档位；`on` 有档、`none` 没档 |
| `images` | 创建请求是否带图 |
| `time` | 这条规则只在此时段命中 |
| `pause` | 条件成立时把 `use` 成员摘出候选 |

两个 `time` 方向相反：**规则的时间窗**是「这类任务只在这个时段走这个成员」；**绑定的时间窗**是「这个渠道在这个时段停用」。

`label` / `member` 是通配匹配，不是语义理解；`intent` 才是让分类器读任务文本判类别。分类器只在开启**且至少一条规则写了 `intent`** 时才调用（否则零开销），判不清就不命中、自然落到后面的规则，并且多花一次小模型调用。

写规则的默认姿势：前面放精确条件（`label`、`member`、`folders`），中间放 `intent`，最后放一条 `continuable:false` 的兜底。删掉兜底等于改掉所有普通子代理的默认行为。

## 七、运行期回退（0.7.10 延迟回退机制）

官方 DSH SDK 的 AgentLoop 仅支持**同 step 同模型 retry**。在 0.7.10 中，为严格遵守宿主在 `preStep` 锁定模型的契约，插件**不再尝试在当前 step 内偷换配置进行跨模型重试**（那会引发 `agent/request proposed ... after step preparation fixed ...` 冲突），而是改为**延迟回退（Deferred Failover）**：

- **只回退可重试的失败**：408 / 429 / 5xx、超时、过载、网络类错误、额度类提示。
- **请求本身的拒绝不回退**：400 / 401 / 403 / 404 / 413 这类换模型也答不对，只会把错误掩盖成「另一个模型也不行」。
- **延迟生效流程**：
  1. 当前 step 发生可重试错误时，推进失败绑定的休息阶梯（按 Retry-After、额度 30 分钟、限流翻倍等阶梯），429 还会被沉底到候选末尾（内存态，重启清空），并在决策记录中记下 `trace deferred`。
  2. 当前 step 的错误**如实交给官方 AgentLoop 处理**（调用 `next()`），由宿主按原生流程抛出或进行同模型重试，**绝不自动重派、不合成伪造消息**。
  3. 当该子 agent / 队员进入**下一个 turn** 时，插件在 `agent/inbox/claimed` 步骤准备前根据已更新的休息/沉底状态，自动从候选链中选择下一项可用候选生效。
- **边界说明**：
  - **明确这不是旧版的当步跨模型自动恢复**。
  - `patience`（0–10）是**最多换几次候选**，用完就放弃并把错误还给你。
  - 手动固定（前 3 级）不参与这套回退。

## 八、新手配置流程

1. **确认模型可用**：先在界面里能正常选到 provider 与 model。
2. **建成员**：填名字（如 `expert`），把渠道按优先级加进绑定；同一模型多渠道就放同一个成员里，这样先换渠道、再换成员。
3. **选排序**：`order` 有明确主次，`rotate` 平均分摊，`weight` 按比例倾斜。
4. **加规则**：先精确、后兜底；不确定就先只写一条兜底，跑通再加。
5. **可选开分类器**：只有按任务语义分流时才开，配一个便宜的小模型。
6. **保存后验证**：跑一个子任务，看设置页的决策记录与用量，确认命中了你以为的成员。

常见诉求：想省钱就把便宜成员设成兜底并降低贵成员权重；想分档就拆成两类条件；某渠道高峰别用就在**绑定**上填停用时段；临时停用成员用界面上的「摘除」；试新模型先建成员 + 一条 `label` 规则，别直接改 `pick`（`pick` 会跳过所有规则）。

## 九、两个示例（讲语义，不是现成配置）

`[PROVIDER_ID]`、`[MODEL_ID]`、`[EFFORT_ID]` 都是占位符，必须换成你自己的值；示例不代表你当前已生效的配置。

**示例 A：省钱档 + 专家档，同一模型走两个渠道**

```jsonc
{
  "members": [
    { "name": "budget", "weight": 6,
      "bindings": [{ "provider": "[PROVIDER_ID_A]", "model": "[MODEL_ID_CHEAP]" }] },
    { "name": "expert", "weight": 2,
      "bindings": [
        { "provider": "[PROVIDER_ID_A]", "model": "[MODEL_ID_STRONG]", "reasoningEffort": "[EFFORT_ID]" },
        { "provider": "[PROVIDER_ID_B]", "model": "[MODEL_ID_STRONG]", "reasoningEffort": "[EFFORT_ID]",
          "time": { "from": "09:00", "to": "12:00" } }
      ] }
  ],
  "rules": [
    { "use": "expert", "label": "*review*" },
    { "use": "budget", "continuable": false }
  ],
  "routing": "weight"
}
```

读法：`expert` 的首选渠道是 A；B 在 09:00–12:00 **停用**，所以这个时段只剩 A，A 失败再退到 `budget`。审核类任务按 `label` 走 `expert`，普通一次性子代理落到 `budget`。

**示例 B：关键词优先 + 意图分流 + 兜底**

```jsonc
{
  "members": [
    { "name": "audit", "bindings": [{ "provider": "[PROVIDER_ID_A]", "model": "[MODEL_ID_STRONG]" }] },
    { "name": "frontend", "bindings": [{ "provider": "[PROVIDER_ID_A]", "model": "[MODEL_ID_MID]" }] },
    { "name": "fallback", "bindings": [{ "provider": "[PROVIDER_ID_B]", "model": "[MODEL_ID_CHEAP]" }] }
  ],
  "rules": [
    { "use": "audit", "label": "*审核*" },
    { "use": "frontend", "intent": "前端界面开发" },
    { "use": "fallback", "continuable": false }
  ],
  "classifier": { "enabled": false, "provider": "", "model": "" }
}
```

读法：两条精确条件在前；`intent` 规则要等分类器打开并配好模型才可能命中（现在关着，所以它不生效）；最后一条兜底保证普通子代理仍有明确归属。

## 十、附录：直接看接口（可选）

界面只是这些接口的外壳。端口用你自己这次 DSH 的 Web 端口（记作 `[DSH_PORT]`）：

- `GET .../api/dsh-team-member-model/state`：当前策略、模型目录、决策记录、休息/沉底状态。
- `GET .../efforts?provider=[PROVIDER_ID]&model=[MODEL_ID]`：该模型公布的思考档位。
- `GET .../usage`：按成员/小时/规则的 token 统计（**不是费用**，DSH 不提供单价）。
- `PUT .../policy`：写整份策略，**全量替换**，漏掉的字段会回默认值；先 GET 回来再改，写操作需要请求头标记。
- `PUT .../teams`：团队固定分配（`target: null` 改新队员默认，`target: 队员 id` 改该队员下一轮），与 `PUT /policy` 不是一回事。

这些接口现在由 **DSH 官方连接鉴权**保护，插件自己不另造 token：本机回环照旧可用，远程/反代能否访问取决于你在
DSH 官方配置里的 `trustedHosts` 与凭据。要直连远程 Host 的接口，请先在那台 Host 上装同版本插件，并带上 DSH 自己的凭据
（本机用 `127.0.0.1`，远程用那台 Host 的地址）。旧版 DSH 没有连接鉴权 API 时会返回
`503 连接鉴权服务不可用，请升级 DSH`——那不是「插件没装」，是宿主太旧。

界面走的是当前会话的官方连接通道（`connection.rpc`），不用页面自己拼 `/api`：所以远程场景下「页面能打开」不等于
「写到了你以为的那台 Host」，以目标 Host 上的状态与用量为准。界面和这些 HTTP 接口读写的是同一份策略/团队/用量。

注意两套路径不要混：**界面/远程调用的 RPC 走本插件自己的 channel `/dsh-team-member-model`**，endpoint 名仍是
`team-member-model/<op>`（例如 `team-member-model/teams`），即 `rpc.call('/dsh-team-member-model', 'team-member-model/teams', …)`。
不能再用 `/api`：官方 `@deepseek-ai/dsh-api-gateway` 独占 `/api` 的单槽 interceptor（0.7.6 因此 405、0.7.7 因此 404，
0.7.8 才真正可用）。而**下面列出的 HTTP 地址仍是 `/api/dsh-team-member-model/*`**，升级不会改它们的写法；
反过来也不能拿 HTTP 路径当 RPC endpoint。

策略、团队、用量都是文件保存，**不要直接改文件指望热更新**：运行时一律走界面或接口。

## 十一、排错顺序

1. **先看决策记录有没有这次创建**。没有也不能直接断定「没进插件」：创建期的记录可能缺失（被调用方自带模型绕过）、请求期现场兜底也没有同等的创建记录；这时要结合该子 agent 自己的请求头（最近一次实际 provider/model）判断。
2. **看结果字段**：被跳过会写明原因（fork 未纳管、目标 provider 没注册、该通道不支持注入、没有可用候选）。
3. **看命中原因**：是规则（含第几条）、`pick`、亲和，还是排序策略；这是「为什么跑了这个模型」的答案。
4. **是不是「下一轮」问题**：团队菜单改完当轮不变属正常；已创建的候选链也不会因改策略而重建。
5. **思考档位灰着**：可能是还在读取（loading）、读取失败、还没选模型，或确实没公布档位——只有 `/efforts` 返回空数组才是「未公布」，别一律当坏掉。
6. **400 类错误不回退**：请求本身被拒绝时，换模型也答不对。
7. **用量对不上**：只统计子 agent，且只有 token 没有金额；没被路由过的会单列。
8. **官方名单里的模型名不算证据**：以最近一次真实请求头为准。

高频追问速答：改了规则现有队员没变 = 候选链创建时已定；`weight` 没感觉 = 只在没命中规则时起作用；`fork` 没被路由 = 默认不纳管；两次跑出不同模型 = 规则没命中落到排序，或上次失败进了休息；成员表清了固定还在 = 那是另一层配置。

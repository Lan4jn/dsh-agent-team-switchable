# 跨 DSH 团队协作桥设计规格

日期：2026-10-18  
状态：设计已确认（已吸收 Task-28 独立审查意见）  
目标版本：DSH 0.2.0-rc.2 及后续版本

---

## 1. 背景与目标

### 1.1 现状与问题

在当前的 DeepSeek Harness（DSH 0.2.0-rc.2）体系中，`agentTeams` 服务严格运行在单一宿主进程（Host）内。官方的核心对象（如 `Agent` 运行时实例、团队成员列表、共享任务看板等）均基于本地内存状态与单机持久化存储，官方框架并未提供任何跨主机（Cross-Host）或分布式的团队协同 API。

当团队需要跨越不同的物理机、工作站或网络节点，让多个各自独立的 DSH 实例协同攻坚时，目前无法原生分发或托管任务。

### 1.2 定位与设计原则

**跨 DSH 团队协作桥（Remote Team Bridge）**旨在为两个各自独立的 DSH 实例架设一条轻量、双向、自治的点对点协作通道。设计遵循以下核心原则：

1. **两端自治，不打破单机核心假设**：各端 DSH 保持独立的运行时生命周期。远端团队如何拆解子任务、调度哪些队员完全由对端自主决定，本端不干涉其内部组织细节。
2. **严守公开接口，无侵入扩展**：仅使用官方公开的 SDK 与服务接口，不进行全局 monkey patch，不篡改官方内部私有状态，不依赖未暴露的内部服务方法。
3. **真实性第一，不伪造本地对象**：严禁在本地 Cordis 上下文中注入虚假的伪造 `Agent` 实例；发起端与接收端的任务 ID 明确映射解耦，不冒用或共享官方内部 `taskID`。
4. **安全可控，Lead 终审**：协作关系必须经双方显式配对授权；任务完成与否由发起端的 Team Lead 独立裁决验收。
5. **保持简单（YAGNI）**：第一期聚焦于可靠的点对点协作、配对鉴权与断线恢复，不引入复杂的多跳网络或分布式共识算法。

## 2. 核心架构与协议边界

### 2.1 拓扑结构

协作桥采用对等（Peer-to-Peer）直连模型。在一次具体的任务委派中，角色划分为：

- **发起端（Caller Host）**：拥有主任务的 Team Lead，负责将部分独立子任务打包委派给外部团队，并接收执行进度与交付产物。
- **接收端（Receiver Host）**：常驻运行的 DSH 实例，通过协作桥监听接入请求，并将远程任务接入本地的团队执行环境。

```text
┌──────────────────────────────────────┐          ┌──────────────────────────────────────┐
│        发起端 (Caller Host)          │          │        接收端 (Receiver Host)        │
│                                      │          │                                      │
│  ┌──────────────┐                  │          │                  ┌──────────────┐    │
│  │  Team Lead   │                  │          │                  │ Remote Lead  │    │
│  └──────┬───────┘                  │          │                  └──────┬───────┘    │
│         │ 委派任务                   │          │                         │ 调度协调   │
│  ┌──────▼─────────────────────────┐  │          │  ┌──────────────────────▼─────────┐│
│  │   协作桥客户端 (Bridge Client)   │  │  直连协议 │  │   协作桥服务端 (Bridge Server)   ││
│  │   - 状态追踪与游标恢复          ├──┼──────────┼─►│   - 端口监听与配对校验         ││
│  │   - 凭据管理                   │  │  (TLS)   │  │   - 会话绑定与生命周期转换     ││
│  └────────────────────────────────┘  │          │  └──────────────┬─────────────────┘│
│                                      │          │                 │ 驱动执行         │
│                                      │          │  ┌──────────────▼─────────────────┐│
│                                      │          │  │ sessionController Remote /     ││
│                                      │          │  │ 本地 Agent Teams 执行环境      ││
│                                      │          │  └────────────────────────────────┘│
└──────────────────────────────────────┘          └──────────────────────────────────────┘
```

### 2.2 公开接口复核与适配

经独立复核 DSH 核心包，跨端交互的底层对接边界如下：

1. **会话控制接口（`sessionController` Remote 签约已严格复核）**：
   - 官方公开的 `ctx.remote.session` 远程命名空间暴露的方法包括：`create`（创建会话）、`prompt`（输入指令并指定 `queue`/`steer` 模式）、`cancel`（取消当轮执行）、`follow`（实时订阅增量事件流）、`page`（拉取分页历史）、`projections`（读取会话投影）、`rename`（重命名）、`updateQueue`（修改排队消息）、`attachment`（读取持久附件）与 `openWorkspacePath`（打开工作区路径）。
   - **注意**：Host 本地服务虽有内部 `inspect` 方法，但其属于进程内私有方法，**未在公开 Remote 接口暴露**。协作桥在远程调用中严禁调用不存在的远程 `inspect`，会话状态查询严格通过公开的 `page`、`projections` 及协作桥自身的专有 RPC 完成。
   - 协作桥服务端将收到的跨端任务转化为接收端本地标准会话的指令投放，并通过 `follow` 实时监听远端会话的输出事件流。
2. **团队管理接口（`agentTeams`）**：
   - `listMembers`、`membership`、`spawnTeammate` 等方法仅作用于当前 Host 内存中的活体 Agent，无法跨进程共享。
   - 协作桥绝不在发起端为远端成员伪造本地 `Agent` 句柄；发起端通过专用的协作桥状态面板或桥接记录展示远程任务进展。

## 3. 连接建立与配对鉴权

### 3.1 网络直连与传输解耦

1. **两端前置**：配对前，双方主机均已独立安装并启动 DSH 运行环境。
2. **监听与通道解耦**：
   - 接收端在配置项 `bridge.port` 中指定监听端口（默认独立端口 `19820`）。
   - 协作桥传输层界定为**双方任意可达的底层 TCP / WebSocket 通道**，不强制绑定公网 IPv6 或特定 DDNS。支持局域网直连、内网穿透端口映射、VPN / WireGuard 虚拟专网通道，或直接暴露的公网 IPv6 / 域名。
3. **TLS 加密与自签证书指纹绑定（TOFU / Pinning）**：
   - 通信协议强制采用 TLS（WSS / HTTPS）。
   - 考虑到点对点通信（尤其 IP 直连与自建 DDNS 场景）通常无法获取公共 CA 签发证书，系统支持 TLS 自签名证书机制。
   - **指纹绑定**：在首次配对握手阶段，发起端获取接收端证书的 SHA-256 指纹并在界面向用户展示核对；确认配对后，该指纹被固化存储（TOFU 机制）。后续每次建立连接均强校验对端证书指纹，严格防范中间人（MITM）攻击与劫持。

### 3.2 首次配对：6 位随机调用码

为防止未授权探测与接入，两台 DSH 首次连接时必须经过交互式人工确认：

```text
发起端 (Caller)                              接收端 (Receiver)
     │                                              │
     │                                     1. 生成 6 位随机调用码
     │                                        (如 "839201", 10 min 有效)
     │                                              │
     │ 2. 输入目标地址与 6 位调用码                  │
     ├─────────────────────────────────────────────►│
     │    HandshakeRequest(code: "839201", fp)      │
     │                                              │ 3. 弹出确认通知:
     │                                              │    "是否允许来自 Host A 的连接?"
     │                                              │    (展示证书指纹与来源 IP)
     │                                              │    [拒绝]  [确认接受]
     │                                              │
     │                                              │ 4. 用户点击接受，生成专属 Token
     │ 5. 协商完成，下发长期凭据与对端指纹          │
     │◄─────────────────────────────────────────────┤
     │    HandshakeResponse(token, serverFp)        │
     │                                              │
     │ 6. 持久化存储长期凭据与服务指纹              │ 7. 持久化记录白名单与客户端指纹
     ▼                                              ▼
```

1. **调用码规范（落实 6 位随机调用码）**：
   - 统一采用**定长 6 位纯数字**（`000000`–`999999`，如 `839201`，不足 6 位前置补零），在人机抄录、口述核对时清晰直观，杜绝大小写及易混淆字符（如 `0/O`、`1/I/l`）。
   - 有效时间固定为 **10 分钟**，单次配对成功或超时后即刻销毁。
2. **防暴力破解与限速锁定**：
   - 针对 6 位数字空间的穷举风险，接收端严格限制尝试频次：同一来源 IP 或配对端点，连续输入错误调用码达到 **5 次**，立即封禁配对 **15 分钟**；
   - 每次握手校验增加 **1 秒** 固定计算延迟，彻底遏制自动化暴力探测。
3. **人工确认**：接收端收到带有效调用码的握手请求后，界面弹出安全提示卡片（展示发起端标识、IP 地址、时间及证书指纹），等待用户显式确认。
4. **生成长期凭据（最小权限原则）**：
   - 用户确认后，两端协商生成专属的长期认证凭据（Bearer Token / HMAC 密钥）。
   - **权限限定**：该 Token **仅限协作桥 Bridge 专用命名空间使用**，绝不包含或复用 DSH 全局 Web GUI 的管理控制凭据，杜绝单点特权外溢。
   - 凭据存储在本地安全数据域中，**严禁打印到普通运行日志、跟踪记录或测试断言中**。
5. **白名单记忆与随时注销**：
   - 接收端持久化记录「已配对设备白名单」（包含对端标识、主机名、配对时间、最后活跃时间与证书指纹）。
   - 接收端提供管理界面与命令，支持查看已配对设备列表并可随时**一键主动注销（Revoke）与拉黑**，注销后该 Token 立即失效。

## 4. 团队接入模式

接收端在承接远端委派的任务时，提供两种接入模式，以适应不同的工作流隔离要求：

### 4.1 模式一：新建专用团队（默认模式）

- **行为**：接收端为该外部协作自动创建独立的专用 Agent Team。
- **命名安全净化（Slug Sanitization）**：
  - 对外部传入的发起端 Host 标识与任务标题执行严格的 Slug 净化：仅保留小写字母、数字与中划线（`^[a-z0-9-]+$`），过滤一切非法标点与路径遍历符号；
  - 命名格式统一为 `bridge-{sanitized-host}-{sanitized-title}`，名称总长截断至最多 **32 字符**；
  - 末尾追加 **4 位** 随机十六进制短后缀（如 `bridge-hosta-task-7f2a`），彻底消除重名覆盖与特殊字符注入隐患。
- **并发团队配额上限（Concurrency Quota）**：
  - 接收端设置最大并发远程专用团队数量（配置项 `bridge.maxConcurrentTeams`，默认上限为 **5 个**）；
  - 达到上限时，新任务直接返回 `QUOTA_EXCEEDED` 拒绝接入，防止无节制建队耗尽系统内存与模型配额。
- **生命周期**：任务交付终审通过后，专用团队可按配置自动归档或保留备查。

### 4.2 模式二：绑定已有团队（可选模式）

- **行为**：接收端允许用户在配置中显式指定将外部协作桥绑定至本地某个既有的活动团队（指定其 Lead Session ID）。
- **调度流程**：外部任务抵达后，作为该已有团队的一个待办事项，直接交由该团队的本地 Team Lead 进行二次分解，并指派给既有的专职队员处理。
- **使用场景**：接收端本身就是一个长期运转的专职流水线（例如专职代码评审团队或测试验证集群）。

### 4.3 团队自治保障

无论采用何种模式，远端团队内部如何进行任务规划、是否创建额外的辅助队友（`spawn_teammate`）、如何分配精力，发起端均不干涉，发起端只对外部任务本身的输入参数与交付质量负责。

## 5. 跨端任务流转与状态机

### 5.1 标识映射与解耦

- **发起端协作任务 ID（`bridgeTaskId`）**：全局唯一字符串（如 `br-task-20261018-xxxx`），由发起端生成，作为跨端网络交互、日志关联与状态同步的主键。
- **本地会话/任务映射**：
  - 发起端记录：`bridgeTaskId` 对应本地哪个父级任务卡片。
  - 接收端记录：`bridgeTaskId` 映射至接收端本地的哪个 `sessionId` 或看板任务。
- **严禁共享官方内部 `taskID`**：两端各自的任务看板存储由各自的 Host 权威管理，绝不跨主机混用自增序号或单机唯一键。

### 5.2 状态机模型

```text
  ┌───────────────┐
  │   submitted   │ 发起端创建并发送任务
  └───────┬───────┘
          │ (30s 超时守卫)
          │ 接收端校验通过并接收入队
  ┌───────▼───────┐
  │   accepted    │ 任务已被远端接收，准备调度 (accepted ≠ done)
  └───────┬───────┘
          │ (3min 停滞看门狗)
          │ 远端团队启动执行
  ┌───────▼───────┐
  │  in_progress  │ 远端队员工作中，持续流式回传事件
  └───────┬───────┘
          │ 远端 Team Lead 提交完整交付物
  ┌───────▼───────┐
  │   reviewing   │ 产物已回传，等待发起端 Lead 终审验收
  └───┬───────┬───┘
      │       │
      │ 驳回  │ 验收通过
      │ (重修)│
      │       ▼
      │ ┌───────────┐
      │ │ completed │ [终态] 任务成功归档
      │ └───────────┘
      │
      └───────► 重新回到 in_progress (带补充反馈 prompt)

 [异常分支]
 任意非终态 ──(不可恢复失败 / 404丢失)──► failed    [终态] 异常中断，释放资源
 任意非终态 ──(发起端主动撤回)────────► cancelled [终态] 经竞态协调后取消执行
```

### 5.3 状态流转规则与超时守卫

1. **`submitted` → `accepted`**：
   - 发起端通过 RPC 投递任务参数（标题、要求、关联上下文文本/引用）。
   - **30 秒握手超时守卫**：若在 30 秒内未收到接收端的明确应答，发起端判定提交超时，任务置为 `failed(SUBMIT_TIMEOUT)`。
   - 接收端校验通过后入队，返回 `accepted` 应答。**特别声明：`accepted` 仅代表接收入队，绝不代表任务已完成（`accepted ≠ done`）**。
2. **`accepted` → `in_progress`**：
   - 接收端开始执行第一轮 Prompt 思考与工具调用。
   - **3 分钟停滞看门狗**：若任务进入 `accepted` 后超过 3 分钟未产生任何事件，发起端触发告警并主动发起状态反查。
3. **`in_progress` → `reviewing`**：远端 Team Lead 判定工作完成，打包交付产物清单与总结说明，推送至发起端。此时接收端状态转为待验收，**无权自行宣布完成**。
4. **`reviewing` → `completed`**：发起端 Team Lead 审查交付结果，判定达到验收标准，发送 `accept` 确认指令，双方置为 `completed` 终态。
5. **驳回修订**：发起端 Team Lead 若认为结果未达标，可调用 `reject` 并附带补充指令，任务退回 `in_progress` 继续调整。

### 5.4 取消与交付完成的并发竞态处理（Cancel vs Reviewing）

当发起端发出取消（`cancel`）操作时，可能存在远端恰好完成并置为 `reviewing` 的临界竞态：

- **裁决原则：以远端权威状态为准，先查后定**。
- 发起端在发送 `cancel` 请求的同时，挂起本地状态转换，并向远端查询原子执行快照：
  - **情况 A（远端成功中断）**：远端在收到取消前未完成交付，成功终止当前执行轮次，返回取消确认。双方一致收敛至 `cancelled` 终态，释放所有资源。
  - **情况 B（远端已交付完成）**：远端在收到取消请求前已完成全部工作并持久化了完整交付包（已处于 `reviewing`）。此时取消请求被判定为“已被交付成果覆盖”，发起端放弃强制标记 `cancelled`，而是将已完成的交付物呈交给发起端 Team Lead 审查。Lead 可在审查阶段根据实际需要选择 `accept` 或重新驳回。

## 6. 游标追溯、断线重连与恢复语义

跨广域网连接容易发生闪断，协作桥必须具备精确的恢复语义。

### 6.1 事件游标（Event Cursor）

- 协作桥传输的所有流式日志、进度事件均携带单调递增的 `seq` 序号。
- 发起端在本地内存与持久化记录中实时维护已确认接收的最大序号 `lastAckSeq`。

### 6.2 断线检测与重连

- **心跳机制**：传输通道维持 15 秒间隔的心跳 Ping/Pong；连续 3 次未收到回包（45 秒）判定连接失活。
- **重试策略**：发起端以指数退避算法（1s、2s、4s、8s……最大 30s）自动尝试重建底层 WebSocket 连接。
- **增量同步**：重连建立后，发起端向接收端发送 `ResumeSubscription(bridgeTaskId, lastAckSeq)`，接收端从 `lastAckSeq + 1` 开始增量补发未送达的事件。

### 6.3 状态不明先查原则（Query-First on Ambiguity）

若在重连过程中发生不可预期的异常（例如网络严重阻塞导致重试超时、接收端服务重启，或发起端本地重启恢复）：

1. **严禁盲目重推**：发起端绝对不能在状态未知时直接重发原任务的创建或 Prompt 请求，以防远端重复执行、产生副作用冲突或污染版本库。
2. **状态先查（`task_query`）**：发起端必须优先调用 `task_query(bridgeTaskId)`，查询该任务在远端的实际执行状态：
   - **若远端仍在执行（`in_progress`）**：重新挂载事件监听流，拉取断线期间的历史日志。
   - **若远端已完成（`reviewing`）**：直接同步最终产物包，进入验收流程。
   - **若远端查无此任务（404 Not Found，如重启丢失未持久化）**：
     - 发起端**立即将本地任务标记为终态 `failed(REMOTE_TASK_LOST)`**；
     - **立即释放该任务占用的所有本地会话引用锁（Session Leases）、等待句柄与并发资源**，杜绝死锁与泄漏；
     - 向发起端 Team Lead 报告详细异常原因，由 Lead 决定是否作为全新任务重新提交。

---

## 7. 产物交付与验收机制

### 7.1 交付物组织形式与作用域约束

远端完成协作后，向发起端提交结构化交付包（Artifact Package）：

1. **执行总结（Summary）**：一段 Markdown 格式的高层次工作概述，包含改动说明、自测情况与关键证据。
2. **文本 Diff 产物（Diff Artifacts）**：
   - 生成的统一补丁（Unified Diff）**严禁全工作区扫描生成**；
   - 必须**严格限定在任务事先声明的 `write_scopes` 范围或专用的 Git 隔离特性分支内生成**，杜绝将远端工作区其他未追踪改动或脏文件误报外泄。
3. **大文件引用产物（Referenced Artifacts）**：
   - 必须提供标准化的结构化元数据：
     - 相对路径严格使用 Posix 格式（禁止以 `/` 开头，严禁包含 `../` 路径穿越）；
     - 包含文件的 SHA-256 校验哈希与确切字节大小（Byte Count）；
     - 附带跨平台环境元数据（如 `os: "darwin", arch: "arm64"`）及必要的文件权限位（如执行位 `mode: 0o755`），保障跨平台还原一致性。

### 7.2 终审裁决权归属

- **唯一裁决者**：任务的成功与否由**发起端 Team Lead**完全负责。
- **禁止自行结项**：接收端或远端团队成员无权在发起端标记任务成功；接收端的「完成」仅代表「提交初稿 / 待验收」。
- 发起端 Team Lead 在确认代码通过本地编译、测试符合要求后，才向发起端看板写入终态。

## 8. 安全边界与权限控制

### 8.1 隔离与凭据保护

1. **无本地特权渗透**：发起端不能利用协作通道在接收端执行任意未声明的 Shell 脚本；所有的操作必须经由接收端预设的 Agent 权限沙箱与工作区规则约束。
2. **防路径穿越**：跨端文件拉取严格限定在当前绑定的工作区目录内部，严禁通过 `../` 或绝对路径读取宿主机系统敏感文件（如 SSH 密钥、系统配置文件等）。
3. **凭据安全与脱敏**：
   - 长期 Token 存储在宿主安全存储域内，限定专属 Bridge 作用域，严禁打入普通日志。
   - 临时 6 位调用码单次使用、定时失效，且必须人工在 UI 确认。

### 8.2 审计日志

两端的协作桥模块必须独立记录清晰的审计日志：
- 发起端记录：任务派发时间、目标主机、调用参数、收到交付的时间与 Lead 验收记录。
- 接收端记录：连接来源 IP、配对时间、执行所用的团队会话 ID、所访问的文件清单与产物回传记录。

## 9. 第一期范围与验收标准 (Phase 1)

### 9.1 包含范围（In Scope）

1. **网络通信与配对**：
   - 支持通过任意可达 TCP / WebSocket 直连（含 IPv6、域名或内网穿透），采用 TLS 自签名证书与 SHA-256 指纹绑定（TOFU）。
   - 首次连接使用定长 6 位纯数字随机调用码（10 分钟有效，5 次错误封禁 15 分钟），接收端人工确认后生成协作专用长期 Token。
   - 接收端提供白名单记忆与随时注销管理。
2. **双模式接入**：
   - 默认模式：自动为远程协作新建隔离的专用团队（命名规范净化，最长 32 字符，含随机短后缀；并发上限默认 5 个）。
   - 绑定模式：支持绑定本地既有的特定团队。
3. **任务流转与状态机**：
   - 实现 `submitted`、`accepted`、`in_progress`、`reviewing`、`completed`、`failed`、`cancelled` 完整流转。
   - 明确 `accepted ≠ done`；包含 30 秒提交超时守卫与 3 分钟停滞看门狗。
   - 包含取消与交付完成的原子竞态裁决机制。
   - 任务标识双向映射解耦，不冒用官方内部 `taskID`，不伪造本地 `Agent`。
4. **断线恢复**：
   - 基于 `seq` 游标的心跳与增量同步。
   - 状态不明时严格执行「先反查状态、再决策下一步」的查询策略；查无此任务（404）时立即标记 `failed(REMOTE_TASK_LOST)` 并释放本地锁与资源。
5. **交付与验收**：
   - 结构化 Markdown 总结、限定在 `write_scopes` 范围内的 Diff 补丁传输。
   - 大文件附带 SHA-256、文件大小、相对路径与 OS/Arch 元数据。
   - 发起端 Team Lead 专享的验收与驳回控制。

### 9.2 明确排除的特性（Out of Scope - YAGNI）

- **不实现多跳中继或去中心化网状网络（Mesh）**：仅支持单对单点对点直连。
- **不实现 NAT 穿透服务（STUN/TURN/UPnP）**：网络可达性依赖外部网络环境（公网 IPv6、静态 IP 或已有内网穿透工具）。
- **不实现跨主机分布式文件系统透明挂载**：产物传输仅采用明确的清单 pull/push 机制。
- **不修改官方内部二进制或源码**：纯插件层扩展。

### 9.3 验收标准 Checklist

- [ ] **配对鉴权验收**：
  - 接收端能够生成定长 6 位纯数字调用码并在 10 分钟后自动过期。
  - 连续输入 5 次错误调用码后，触发 15 分钟临时封禁。
  - 发起端首次连接校验并绑定对端 TLS 证书指纹；接收端弹出确认框，确认后生成仅限 Bridge 作用域的长期 Token。
  - 接收端界面可查看白名单，点击注销后对端立即无法访问。
- [ ] **执行与接入验收**：
  - 专用团队命名符合 `bridge-{host}-{title}-{hash}` 规范且总长不超过 32 字符；并发团队超过 5 个时正确返回 `QUOTA_EXCEEDED`。
  - 绑定已有团队模式下，任务正确分发给本地既有团队。
  - 官方远程 RPC 仅调用已验证公开方法（`create`/`prompt`/`cancel`/`follow`/`page`/`projections`），无未验证私有方法调用。
- [ ] **状态机与超时竞态验收**：
  - 30 秒提交无应答触发超时失败；`accepted` 停滞超过 3 分钟触发看门狗。
  - 发起端取消与远端交付完成发生竞态时，以远端快照为准正确裁决。
  - 接收端回传状态标记为 `reviewing`，不可直接标记为 `completed`。
- [ ] **断线恢复与 404 收尾验收**：
  - 人工中断网络 20 秒后恢复，双方自动重连并根据 `lastAckSeq` 增量补齐丢失日志。
  - 状态不明时发起端优先调用 `task_query`；若收到 404 错误，本地任务收敛为 `failed(REMOTE_TASK_LOST)`，会话引用锁即刻释放。
- [ ] **交付物与安全验收**：
  - Unified Diff 严格限制在 `write_scopes` 范围内，无无关文件脏改动。
  - 大文件传输附带准确的 SHA-256、文件大小与 OS/Arch 元数据。
  - 发起端 Team Lead 拥有最终终审权，可执行 `accept` 结项或 `reject` 驳回。
- [ ] **排版与规范验收**：
  - 文档严格遵循中英文混排空格与全角标点规范，无语法与格式问题。

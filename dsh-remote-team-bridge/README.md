# 跨 DSH 团队协作桥 (Remote Team Bridge)

`dsh-remote-team-bridge` 是一个为 DeepSeek Harness (DSH 0.2.0-rc.2 及后续版本) 设计的对等（Peer-to-Peer）团队协同插件。它允许不同物理机、工作站或网络节点上的两个独立 DSH 实例，通过安全的点对点直连通道委派并协同执行复杂的长程团队任务。

---

## 核心设计与安全原则

1. **两端自治**：两端 DSH 保持独立的运行时与生命周期。远端团队内部如何拆解子任务、调度哪些队员完全由对端自主决定，本端不干涉其内部组织细节。
2. **严守公开接口**：会话控制严格基于官方公开的 `sessionController` Remote 接口（`create`、`prompt`、`cancel`、`follow`、`page`、`projections`）；不使用任何未暴露的私有内部方法，不进行全局 monkey patch。
3. **真实性第一**：严禁在本地伪造虚拟 `Agent` 句柄；发起端与接收端的任务 ID 双向映射解耦，绝不跨主机共享官方内部 `taskID`。
4. **安全可控，Lead 终审**：协作关系必须经双方显式配对授权；任务完成与否由发起端的 Team Lead 独立裁决验收（`accepted ≠ done`）。
5. **最小权限与日志脱敏**：配对签发的长期 Token 仅对协作桥 Bridge 专用命名空间有效，绝不赋权全局 Web GUI；Token 严禁打印到普通日志。

---

## 配置与启用

为了防止安装即对外开放网络端口造成安全隐患，**插件默认处于完全未启用状态（`enabled: false`）**。

### 配置项说明

在 DSH 的插件配置中支持以下字段：

| 配置项 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `enabled` | boolean | `false` | 是否开启协作桥监听服务（默认关闭） |
| `port` | number | `19820` | 接收端监听端口（可配置为任意可用端口） |
| `host` | string | `::` | 监听绑定的网络接口（默认 `::` 支持 IPv6/IPv4 双栈） |
| `maxDedicatedTeams` | number | `5` | 接收端允许同时并发运行的最大专用团队数 |

### 网络与传输支持

协作桥基于标准 HTTPS / WebSocket 传输，底层界定为**双方任意可达的 TCP 通道**：
- 局域网直连或同机回环（如 `::1` 或 `127.0.0.1`）；
- 内网穿透、端口映射或自建 WireGuard / VPN 虚拟局域网；
- 公网 IPv6 直连或已绑定 DDNS 域名的公网主机。

系统采用 TLS 自签名证书与 **首次信任（TOFU / Pinning）** 机制。首次连接时发起端校验接收端证书的 SHA-256 指纹并在界面供用户核对，确认后永久固化该指纹，严格防范中间人劫持。

## 首次配对流程：6 位随机调用码

两台 DSH 首次连接时，必须经过交互式人工确认：

1. **生成调用码**：
   - 接收端用户在协作桥面板点击「允许配对」；
   - 系统生成一个**定长 6 位纯数字随机调用码**（如 `839201`），有效时间固定为 **10 分钟**，单次有效。
2. **防暴力破解与限速保护**：
   - 同一来源 IP 连续 5 次输入错误调用码，系统立即自动封禁该来源 **15 分钟**；
   - 每次握手校验增加 1 秒固定计算延迟，杜绝自动化爆破。
3. **发起握手与人工确认**：
   - 发起端输入接收端的主机地址、端口与该 6 位调用码；
   - 接收端界面弹出安全确认卡片，展示发起端标识、IP 地址及证书指纹；
   - 接收端用户点击「确认接受」后，两端协商生成专属的长期认证 Token。
4. **白名单与注销管理**：
   - 接收端在持久化存储中维护已配对设备白名单；
   - 用户可随时在界面查看已配对设备列表，并支持一键主动撤销（Revoke），撤销后对端凭据即刻失效。

## 两种团队接入模式

接收端在承接远端委派的任务时，支持两种接入模式：

### 模式一：新建专用团队（默认模式）

- 接收端自动为外部协作创建独立的专用 Agent Team。
- **命名安全净化（Slug Sanitization）**：外部传入的发起端标识与任务标题经由严格过滤（仅保留字母数字中划线），截断至最多 32 字符，并自动追加 4 位十六进制短随机后缀（例如 `bridge-hosta-task-7f2a`），彻底避免名称冲突与特殊字符注入。
- **并发配额保护**：当活动专用团队达到 `maxDedicatedTeams`（默认 5 个）上限时，新任务直接拒绝并返回 `QUOTA_EXCEEDED`，防止资源耗尽。
- 任务结项验收后，专用团队可自动归档或保留备查。

### 模式二：绑定已有团队（可选模式）

- 接收端用户可显式指定将外部协作挂载到本地某个既有的活动团队（指定其 Lead Session ID）。
- 外部任务作为该团队的一个待办项，由本地 Team Lead 统一规划并分发给既有队员。

## 任务流转、状态机与恢复语义

### 状态流转规则

```text
submitted ──(30s 超时)──► accepted ──(3min 看门狗)──► in_progress ──► reviewing ──► completed
   │                         │                            │              │
   ▼                         ▼                            ▼              ▼
failed(SUBMIT_TIMEOUT)   failed(STALL)                 cancelled      rejected
```

- **`accepted ≠ done`**：`accepted` 仅表示任务已被远端接收并入队，绝不代表任务完成。
- **30 秒提交超时守卫**：发起端投递任务后，若 30 秒内未收到接收端确认，自动标记为提交超时。
- **3 分钟停滞看门狗**：任务进入 `accepted` 后若超过 3 分钟未产生任何事件，发起端触发告警并启动状态反查。
- **取消与交付完成并发竞态（Cancel vs Reviewing）**：
  - 当发起端发出取消指令时，坚持**“以远端真实快照为准、先查后定”**原则；
  - 若远端在取消前已完成交付并持久化为 `reviewing`，发起端放弃强制中断，将交付物呈交发起端 Lead 审查；若远端尚未交付，则双方收敛至 `cancelled` 终态。

### 断线重连与状态不明先查原则

- 通道内事件流附带单调递增的 `seq` 序号，保持 15 秒心跳 Ping/Pong。
- 网络闪断时，发起端自动按指数退避（1s → 2s → 4s……最大 30s）重连，重连后携带 `lastAckSeq + 1` 增量补发未送达事件。
- **状态不明先查（Query-First on Ambiguity）**：若发生网络严重中断或服务重启，发起端**严禁盲目重发任务**，必须优先调用 `task_query`：
  - 远端仍在执行（`in_progress`）：重新挂载事件监听；
  - 远端已交付（`reviewing`）：直接拉取交付包；
  - 远端查无此任务（404 Not Found）：本地立即标记为 `failed(REMOTE_TASK_LOST)`，并即刻释放本地所有关联会话引用锁与资源，杜绝死锁与泄漏。

## 产物交付与安全隔离

1. **Unified Diff 作用域保护**：
   - 回传的统一补丁（Unified Diff）**严禁全工作区扫描生成**；
   - 必须严格限定在任务事先声明的 `write_scopes` 范围或专用的 Git 隔离特性分支内生成，杜绝无关文件脏改动外泄。
2. **大文件传输规范**：
   - 相对路径严格使用 Posix 格式（禁止以 `/` 开头，严禁包含 `../` 路径穿越）；
   - 强制包含文件的 SHA-256 校验和、确切字节大小、跨平台环境元数据（`os` / `arch`）及文件权限位（如执行权限）。
3. **发起端 Lead 独占终审权**：
   - 接收端无权自行标记完成；唯有发起端 Team Lead 拥有最终终审权，在本地验证测试通过后方可下发 `accept` 归档结项。

## 常见错误码表

| 错误码 | 说明 | 处理建议 |
|---|---|---|
| `SUBMIT_TIMEOUT` | 任务提交在 30 秒内未收到接收端入队响应 | 检查网络连通性或接收端负载后重试 |
| `PAIRING_BLOCKED` | 连续 5 次输入错误调用码，进入 15 分钟临时封禁 | 等待 15 分钟封禁解除后重新配对 |
| `FINGERPRINT_MISMATCH` | 接收端证书指纹与首次信任绑定的指纹不匹配 | 存在中间人风险或对端重置了证书，需核实安全后重新绑定 |
| `REMOTE_TASK_LOST` | 远端查无此任务（404，如重启且未持久化） | 发起端已释放本地资源锁，由 Lead 决策是否重新提交 |
| `QUOTA_EXCEEDED` | 接收端活动专用团队已达并发上限（默认 5 个） | 等待对端既有协作任务归档释放配额 |
| `DIGEST_MISMATCH` | 回传文件的 SHA-256 哈希校验失败 | 传输损坏或文件被篡改，需重新拉取产物 |

## 已知限制与环境要求

1. **依赖 OpenSSL**：TLS 自签名证书生成依赖宿主系统包含 `openssl` CLI 工具。
2. **协议版本一致性**：双端必须运行相互兼容的协作桥协议版本。
3. **跨系统验证边界**：当前自动化回归已在本机覆盖双实例回环；跨物理机公网穿透及异构操作系统（如 macOS 与 Windows / Linux 混部）需依赖外部网络路由可达性，建议结合 VPN 或 IPv6 环境使用。
